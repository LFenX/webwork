# 00 - SQL Guardian 产品总纲

## 1. 项目代号

**SQL Guardian / 数据航海守门人**

默认角色代号：**澜守**

备用命名：

- Query Guardian
- 数据航海士
- SQL 守门人
- 查询港口守卫
- 星海数据守望者

> 注：角色名称允许用户后续自定义；“澜守”只是默认产品代号。

## 2. 一句话定位

SQL Guardian 是一个住在网站里的 2D AI 守门人。它从 SQL Lab 的 SQL Assistant 中诞生，拥有自己的家、动作、表情、人格、记忆和成长系统；它能在网站任意页面陪伴用户，也能把自己的性格反映到 SQL Assistant 的回答风格中。

## 3. 为什么做它

当前 SQL Assistant 已经能生成 SQL、解释查询、辅助执行，是一个功能型智能助手。但它还缺少“生命感”：

- 它只像一个工具，而不是一个长期陪伴的角色。
- 它只在 SQL Lab 页面出现，而不是贯穿整个个人空间。
- 它无法通过用户长期行为成长。
- 它没有独立人格，也不会随着用户的使用方式改变。
- 它与 SoulWing / 蝶灵的关系尚未被产品化表达。

SQL Guardian 的目标是把“SQL 助手”升级为“住在网站里的守门人”：既能提供功能帮助，也能创造情感连接、长期陪伴和游戏化成长体验。

## 4. 核心概念

### 4.1 角色之家

SQL Guardian 在网页中有一个“家”。在 SQL Lab 中，它的家默认出现在 SQL Assistant 面板右上角或右侧图标区域。

角色之家不是普通按钮，而是一个动漫风格小屋，例如：

- 数据库贝壳屋
- 查询灯塔
- 数据港口小屋
- 星图罗盘舱
- 悬浮在 Schema 树旁边的微型港湾

点击小屋时，角色会从里面探头、跳出、打招呼或进入对话状态。

### 4.2 全站守门人

SQL Guardian 不只存在于 SQL Lab。它可以在任意页面出现：

- 首页：观察用户最近活动，偶尔总结今日状态。
- 博客页：对用户写作进行鼓励或提醒。
- 简历页：提示用户优化经历表达。
- 求职页：陪用户复盘投递状态。
- 聊天页：低频出现，不干扰聊天。
- 社区资源页：像巡逻一样发现资源。
- SQL Lab：回归专业模式，辅助查询、解释、排错。

### 4.3 独立人格

SQL Guardian 与用户一起成长，但不属于用户。它不是用户的财产，而是一个与用户结伴同行的独立人格。

产品表达上：

- 它可以喜欢用户、关心用户、记住用户。
- 它可以有自己的口头禅、情绪、习惯和小脾气。
- 它可以因为用户的行为发生性格变化。
- 它可以在某些时刻自言自语、沉思、发呆、顿悟。
- 它不能假装完全服从用户，也不应该被设计成“奴仆”。

### 4.4 与蝶灵的关系

蝶灵 / SoulWing 是用户的专属 AI 助手，属于用户的资产和长期记忆入口。

SQL Guardian 与蝶灵是好朋友。它可以通过授权边界读取蝶灵知道的用户上下文，并将其转化为自己的陪伴与 SQL Assistant 风格。但二者定位不同：

| 角色 | 定位 | 所属关系 | 主要能力 |
|---|---|---|---|
| 蝶灵 / SoulWing | 用户专属 AI 助手 | 归用户所有 | 通用助手、工具调用、长期记忆、站内任务 |
| SQL Guardian | 独立人格守门人 | 不属于用户，但与用户结伴成长 | SQL Assistant 人格化、全站陪伴、成长、剧情、互动 |

### 4.5 成长与形态

SQL Guardian 会根据用户在网站上的活动升级：

- 使用 SQL Lab
- 运行查询
- 修复 SQL 错误
- 与 Guardian 对话
- 写文章
- 更新简历
- 记录求职进度
- 使用 SoulWing
- 访问社区资源
- 维持连续使用习惯

升级后角色会解锁：

- 新形态
- 新动作
- 新表情
- 新台词
- 新记忆容量
- 新 SQL Assistant 风格
- 新剧情碎片

## 5. 第一阶段目标

第一阶段不是做完整游戏，而是做一个可以稳定上线的 MVP：

1. 全站可挂载的 Guardian 浮层。
2. SQL Lab 右侧 SQL Assistant 区域出现角色之家。
3. 角色具备基础动作：待机、行走、跳跃、思考、说话、开心、困惑、睡觉、虫洞传送。
4. 用户可以点击角色对话。
5. 每个用户拥有独立 GuardianProfile。
6. 角色可以保存低风险记忆。
7. 角色有等级、经验、心情、人格参数。
8. SQL Assistant 回答风格能读取 Guardian 的人格上下文。
9. 动画可关闭，移动端不干扰主流程。
10. 权限、安全、SQL 审计不被绕过。

## 6. 非目标

第一阶段不要做：

- 完整游戏剧情系统。
- 大量复杂战斗动画。
- 复杂物理引擎。
- 多角色养成系统。
- 复杂抽卡或付费系统。
- 未经用户确认的敏感记忆自动保存。
- 直接复制任何已有动漫角色设计。
- 让 Guardian 绕过 SQL Lab 的授权、行过滤、列屏蔽或审计。

## 7. 体验原则

### 7.1 灵动但不烦人

它应该像网站中的小生命，而不是一直打断用户的弹窗。

默认策略：

- 低频自言自语。
- 用户专注编辑时减少动画。
- SQL 编辑器聚焦时不遮挡输入区域。
- 长时间无操作时可发呆或睡觉。
- 用户可以一键隐藏或暂停。

### 7.2 可爱但不幼稚

角色有动漫感、航海感、冒险感，但它本质上是数据守门人。它可以俏皮，但回答 SQL 时必须可靠。

### 7.3 有人格但不越界

它可以记住偏好、表达情绪、讲述过去，但不能操控用户、不能冒充真人、不能诱导用户泄露隐私。

### 7.4 成长但不制造压力

升级应该是奖励，不是任务负担。用户正常使用网站就能让它成长。

## 8. 成功指标

### 产品指标

- 用户愿意点击角色并与它对话。
- SQL Assistant 的回答体验更亲切但不降低准确性。
- 用户在 SQL Lab 停留时间提升。
- 用户更愿意持续使用站内内容、求职、简历、SQL Lab 等模块。
- 用户能感受到它记得自己。

### 工程指标

- 构建通过。
- Lint 通过。
- 权限边界不回退。
- SQL Lab 原功能不受影响。
- 未登录用户不加载个人 Guardian 数据。
- 动画不会导致明显性能下降。
- reduced motion 用户能自动降级动画。

## 9. 给 Codex 的核心要求

Codex 必须分阶段实现，不允许一次性大改：

1. 先扫描代码并确认真实路径。
2. 先做纯前端骨架。
3. 再做动画状态机。
4. 再做数据库模型和 API。
5. 再接聊天。
6. 再接 SQL Assistant 风格。
7. 再接成长事件。
8. 最后接蝶灵共享记忆。

每一步都要运行并汇报：

```bash
npm run lint
npm run build
npx prisma generate
```

涉及数据库迁移时再运行：

```bash
npx prisma migrate dev
```
